\chapter{Installazione e configurazione}

\intro{In questo capitolo vengono forniti i prerequisiti e le indicazioni per l'installazione e il \emph{setup} di OpenMetadata in ambiente locale.}\\

\section{Prerequisiti}
L'installazione e l'esecuzione di OpenMetadata prevedono requisiti specifici, legati alle risorse hardware della macchina ospitante e 
all'ambiente di esecuzione locale, basato in questo contesto sulla containerizzazione tramite Docker.

Per garantire il corretto funzionamento di una distribuzione locale di test, la macchina ospitante (basata su sistema operativo Linux oppure su Windows 
tramite \gls{wsl}2 o macchina virtuale\footnote{Si è scelto di non utilizzare Docker Desktop, la cui licenza d'uso commerciale richiede un abbonamento a pagamento per aziende di determinate dimensioni, optando invece per l'installazione diretta di Docker Engine all'interno di un ambiente Linux (WSL2 o macchina virtuale).}) deve allocare al Docker Engine le seguenti risorse hardware minime:
\begin{itemize}
    \item \textbf{CPU}: Almeno 4 vCPU.
    \item \textbf{Memoria RAM}: Almeno 6--8 GB di RAM interamente dedicati ai container.
    \item \textbf{Spazio su disco}: Almeno 30--40 GB di spazio libero.
\end{itemize}

Dal punto di vista software, i requisiti fondamentali prevedono Git per il controllo di versione, Docker Engine (versione 20.10.0 o superiore) e Docker Compose (versione v2.1.1 o superiore). 
L'architettura locale di OpenMetadata viene orchestrata attraverso quattro container distinti:
\begin{enumerate}
    \item \textbf{Database di sistema}: Un'istanza PostgreSQL o MySQL dedicata al salvataggio dello stato, delle configurazioni e dei metadati gestiti dalla piattaforma.
    \item \textbf{OpenMetadata Server}: Il backend centrale della piattaforma sviluppato in Java.
    \item \textbf{OpenMetadata Ingestion (\emph{Apache Airflow})}: Il motore di orchestrazione responsabile dell'esecuzione automatica e pianificata delle pipeline di estrazione dati.
    \item \textbf{Motore di ricerca}: Un container ElasticSearch (o \gls{opensearch}) dedicato all'indicizzazione dei metadati e alla ricerca \emph{full-text}.
\end{enumerate}

Per consentire la corretta fruizione dei servizi sul browser, l'ambiente di rete locale deve garantire che le porte 8585 (dedicata all'interfaccia utente di OpenMetadata) 
e 8080 (dedicata al pannello di controllo di Apache Airflow) siano libere da conflitti.

Infine, per testare la piattaforma senza violare i vincoli di riservatezza sui dati reali aziendali, durante lo stage è stato utilizzato il 
database relazionale di esempio \emph{AdventureWorks} fornito da Microsoft\cite{site:adventureworks}. 
Tale risorsa è stata ripristinata all'interno di un'istanza locale di Microsoft SQL Server, simulando uno scenario di produzione realistico, completo di 
relazioni e chiavi esterne su cui eseguire le prime procedure di \emph{Data Ingestion} e \emph{Data Discovery}.

\section{Installazione di OpenMetadata}
Una volta soddisfatti tutti i prerequisiti, la procedura di deployment locale di OpenMetadata è stata eseguita tramite Docker e Docker Compose, 
seguendo i passaggi della documentazione ufficiale\cite{site:openmetadata-docs}, di seguito elencati:
\begin{enumerate}
    \item \textbf{Creazione della directory di lavoro}: è stata creata una cartella dedicata al progetto:
    \begin{verbatim}
mkdir openmetadata-docker && cd openmetadata-docker
    \end{verbatim}
    \item \textbf{Download del file di configurazione}: è stato scaricato il file \texttt{docker-compose.yml} ufficiale dal repository\cite{site:openmetadata-repo} del progetto (oppure il file \texttt{docker-compose-postgres.yml} qualora si preferisca utilizzare PostgreSQL come database di sistema al posto di MySQL).
    \item \textbf{Avvio dei servizi}: i container Docker di OpenMetadata sono stati eseguiti tramite il seguente comando:
    \begin{verbatim}
docker compose -f docker-compose.yml up --detach
    \end{verbatim}
    \item \textbf{Verifica dello stato dei container}: tramite il comando \texttt{docker ps} è stato verificato che tutti e quattro i container risultassero effettivamente in esecuzione (stato \texttt{Up}), prima di procedere con l'accesso alla piattaforma.
\end{enumerate}

\noindent Una volta che i container risultano operativi, la piattaforma è pronta per l'utilizzo:
\begin{itemize}
    \item \textbf{Interfaccia utente di OpenMetadata}: raggiungibile da browser all'indirizzo \nolinkurl{http://localhost:8585}. Al primo accesso, l'autenticazione avviene tramite le credenziali di default fornite dal sistema: \texttt{admin@open-metadata.org} come \emph{username} e \texttt{admin} come \emph{password}. Da qui è poi possibile accedere alle impostazioni generali e configurare nuovi utenti;
    \item \textbf{Pannello di controllo di Apache Airflow}: raggiungibile all'indirizzo \nolinkurl{http://localhost:8080} inserendo le credenziali di default (\texttt{admin} / \texttt{admin}). Airflow opera in background come motore di orchestrazione per le pipeline di \emph{ingestion} dei metadati; sebbene la gestione delle sincronizzazioni avvenga interamente dall'interfaccia di OpenMetadata, l'accesso diretto ad Airflow risulta fondamentale per l'analisi dei log e il \emph{debugging} avanzato in caso di fallimento delle pipeline.
\end{itemize}

\section{Data Ingestion}
\label{sec:data_ingestion}
La \emph{Data Ingestion} costituisce il processo attraverso cui OpenMetadata si connette alle sorgenti dati aziendali esterne (come database relazionali, fogli di calcolo, 
piattaforme di Business Intelligence o sistemi di \emph{storage}) per estrarne e indicizzarne le informazioni strutturali e descrittive.

Prima di analizzare i dettagli operativi, è opportuno fare una premessa: la \emph{Data Ingestion} non importa, non duplica e non 
memorizza in alcun modo i dati reali all'interno del catalogo. La piattaforma si occupa esclusivamente di analizzare e scansionare le fonti originali per estrarne i metadati. 
Nello specifico, la piattaforma opera nel rispetto dei seguenti vincoli:
\begin{itemize}
    \item \textbf{Accesso in sola lettura (\emph{Read-Only})}: OpenMetadata si connette alle fonti dati esterne utilizzando credenziali dotate dei soli permessi di lettura sulle viste di sistema e sugli schemi dei dati.
    \item \textbf{Integrità dei dati reali}: Il catalogo non possiede autorizzazioni di scrittura, modifica o cancellazione sui database sorgente; è escluso qualsiasi rischio di alterare o compromettere i record reali dell'azienda.
    \item \textbf{Estrazione dei soli metadati}: La piattaforma acquisisce esclusivamente i \textbf{metadati}, ovvero informazioni quali nomi delle tabelle, tipi di dato delle colonne, chiavi primarie, vincoli relazionali, descrizioni e statistiche aggregate.
    \item \textbf{Gestione dei dati campione}: I dati prelevati per la profilazione o la classificazione automatica vengono acquisiti come \emph{Sample Data} e resi consultabili all'interno della scheda di ciascun asset. L'accesso a tali campioni resta comunque soggetto al sistema di controllo degli accessi della piattaforma: qualora una colonna venga classificata come dato sensibile, i relativi valori campione vengono automaticamente oscurati nell'interfaccia per tutti gli utenti privi del ruolo di \emph{Owner} o \emph{Admin} sull'asset, come approfondito nel Capitolo~\ref{cap:sviluppo-sicuro}.
\end{itemize}

\subsection{Configurazione di un nuovo servizio}
La configurazione di un nuovo servizio di database (per esempio Microsoft SQL Server o PostgreSQL) avviene tramite l'interfaccia di amministrazione della piattaforma e prevede i seguenti passaggi:
\begin{enumerate}
    \item \textbf{Selezione del connettore nativo}: viene individuato il \gls{dbms} sorgente dall'elenco dei connettori supportati;
    \item \textbf{Parametri di connessione e di rete}: vengono inseriti l'indirizzo IP dell'\emph{host}, la porta di comunicazione dedicata e il nome del database da scansionare (per esempio il database \emph{AdventureWorks});
    \item \textbf{Credenziali dedicate}: vengono fornite le credenziali di accesso, profilate secondo il \gls{minimoprivilegio} (\emph{Principle of Least Privilege}), sufficienti per accedere alle tabelle di sistema;
    \item \textbf{Verifica e filtri di inclusione}: dopo aver testato la connessione, vengono definite eventuali regole di filtraggio tramite espressioni regolari per limitare la scansione a specifici schemi o tabelle di interesse.
\end{enumerate}

Completata la fase di \emph{ingestion}, ogni data asset importato è accessibile attraverso una scheda di dettaglio dedicata. 
L'interfaccia raccoglie in un'unica vista i metadati generali, come la fonte di provenienza, l'\emph{owner}, il livello di importanza del dataset (\emph{tier}),

\subsection{Modifica dei metadati tramite Bulk Import \& Export}
Per facilitare la gestione del catalogo su larga scala, OpenMetadata supporta la funzionalità di \emph{Bulk Import} \& \emph{Export} tramite file in formato CSV per tutti i principali asset. 

L'operazione di \textbf{Bulk Export} consente di scaricare in locale un file CSV contenente l'inventario completo dei metadati di un asset. Tale file funge anche da modello per la successiva fase 
di \textbf{Bulk Import}: l'utente può aggiornare o arricchire offline i metadati di un asset, per poi ricaricare il CSV sulla piattaforma. 
Prima di applicare le modifiche, OpenMetadata mostra un'anteprima di validazione in tempo reale che permette di verificare e correggere eventuali errori direttamente da browser.


\section{Ricerca e Data Discovery}
La funzionalità di \emph{Data Discovery} rappresenta il principale punto di accesso al catalogo dati. È accessibile da qualsiasi pagina tramite la barra di ricerca posta in alto. 
Nella pratica, OpenMetadata funziona come un vero e proprio motore di ricerca interno: permette a tutti gli utenti di trovare velocemente le informazioni relative a qualsiasi asset aziendale.

\subsection{Ricerca semplice e filtri rapidi}
La ricerca semplice consente di individuare le risorse di interesse digitando parole chiave in testo libero. Il motore di ricerca interno confronta la query dell'utente con i nomi 
degli asset ed estende la ricerca anche alle descrizioni testuali, ai nomi di singole colonne di una tabella o ai grafici di un report.

I risultati vengono restituiti in tempo reale, suddivisi per tipologia di risorsa, e possono essere filtrati attraverso l'impiego dei \emph{Quick Filter}. 
Questi ultimi permettono di restringere il perimetro di esplorazione in base a parametri chiave come la fonte di provenienza, il dominio aziendale o i tag di classificazione.

\subsection{Ricerca avanzata tramite Query Builder}
Per gestire cataloghi complessi e grandi volumi di metadati, OpenMetadata mette a disposizione la funzionalità di ricerca avanzata (\emph{Advanced Search}), 
basata su un \emph{query builder} visuale. Questo strumento consente di comporre interrogazioni complesse combinando molteplici condizioni attraverso gli operatori logici
 \texttt{AND} e \texttt{OR}. I filtri possono essere applicati a diversi parametri chiave, tra cui:
\begin{itemize}
    \item \textbf{\emph{Owner}}: Il proprietario o il team responsabile dell'asset.
    \item \textbf{\emph{Tag}}: La classificazione di sicurezza o riservatezza assegnata (es. \texttt{PII.Sensitive}).
    \item \textbf{\emph{Tier}}: Il livello di importanza strategica dell'\emph{asset} per l'organizzazione.
    \item \textbf{\emph{Service} e \emph{Database Schema}}: Il servizio di origine e lo schema logico di appartenenza.
    \item \textbf{\emph{Column}}: La presenza di specifiche colonne all'interno della struttura della tabella.
\end{itemize}

Attraverso gli operatori di confronto messi a disposizione (tra cui \emph{Equal to}, \emph{Any in}, \emph{Contains} e le rispettive negazioni), l'utente può formulare interrogazioni 
mirate, quali ad esempio: \emph{"Mostra tutte le tabelle del database AdventureWorks, schema SalesLT, che possiedono il tag PII.Sensitive e il cui proprietario è un Admin"}.

\subsection{Ricerca semantica con embedding vettoriali}
Dal punto di vista architetturale, è opportuno distinguere i due motori di ricerca integrabili nella piattaforma:
\begin{itemize}
    \item \textbf{Ricerca \emph{Full-Text} (Elasticsearch)}: Configurazione predefinita nelle installazioni locali standard; garantisce un'indicizzazione rapida e risposte ad altissima velocità basate sulla corrispondenza esatta di parole chiave e sottostringhe.
    \item \textbf{Ricerca semantica (OpenSearch)}: Funzionalità avanzata destinata agli ambienti di produzione; richiede OpenSearch come backend e si integra con servizi esterni di \emph{embedding} vettoriali (come OpenAI o AWS Bedrock).
\end{itemize}

A differenza della ricerca testuale tradizionale, la ricerca semantica elabora il significato concettuale della query inserita, analizzandola tramite \emph{embedding} vettoriali anziché affidarsi alla semplice corrispondenza dei termini. 
Questo approccio permette agli utenti di interrogare il catalogo in linguaggio naturale. 
Il sistema quindi restituisce risultati pertinenti anche se i termini ricercati non compaiono esplicitamente nei nomi tecnici delle colonne o delle tabelle.

Essendo vincolata all'impiego di OpenSearch e di \emph{provider} AI esterni, tale funzionalità non è supportata da Elasticsearch e risulta pertanto non disponibile 
nell'installazione locale di default, ma rappresenta un'evoluzione strategica per le infrastrutture su larga scala.


\section{Data Lineage}
Il \emph{Data Lineage} rappresenta la mappatura del ciclo di vita del dato, dalla sua origine fino alla destinazione finale. All'interno di un catalogo aziendale, 
questo concetto si traduce nella rappresentazione visiva ed \emph{end-to-end} del percorso e delle trasformazioni delle informazioni, 
illustrando come queste vengano estratte dalle sorgenti primarie, elaborate attraverso \emph{pipeline} di trasformazione e, infine, esposte nei report aziendali.

\subsection{Livelli di granularità}
All'interno di OpenMetadata, il grafo del \emph{lineage} viene ricostruito in modo automatico dal \emph{Lineage Agent}, che analizza i log delle query SQL 
eseguite sulle fonti originali, le definizioni delle viste e le configurazioni degli strumenti di BI, ricostruendo le relazioni di dipendenza secondo due principali livelli di granularità:
\begin{itemize}
    \item \textbf{Table-Level Lineage}: Mostra le connessioni ad alto livello tra intere entità (database, tabelle e report), ricostruendo il percorso \emph{end-to-end} del dato dalla sorgente (\emph{upstream}) fino alla destinazione finale (\emph{downstream}).
    \item \textbf{Column-Level Lineage}: Traccia il percorso di derivazione fino al dettaglio della singola colonna. Questa funzionalità risulta fondamentale ai fini della conformità al GDPR, poiché permette di verificare esattamente come un campo contenente dati personali o sensibili si propaga tra le tabelle e i sistemi aziendali.
\end{itemize}


Qualora vi siano trasformazioni non tracciabili direttamente dai log SQL, OpenMetadata mette a disposizione un editor visuale \emph{no-code} (\textbf{\emph{Lineage} manuale}) 
basato su meccanismi \emph{drag-and-drop}, consentendo agli utenti autorizzati di creare o integrare manualmente nodi e collegamenti.

\subsection{Analisi di impatto e livelli informativi}
L'applicazione operativa più rilevante del \emph{Column-Level Lineage} è la cosiddetta \textbf{\emph{Impact Analysis}} (Analisi di Impatto). 
Prima di apportare modifiche strutturali a una colonna o a una tabella (ad esempio l'eliminazione di un campo o il cambio del tipo di dato), l'utente può consultare il grafo 
per identificare preventivamente quali tabelle, \emph{pipeline} e report verrebbero impattati o coinvolti da tale modifica.

L'interfaccia di visualizzazione del \emph{lineage} supporta inoltre l'attivazione di diversi livelli informativi (\emph{Layers}):
\begin{itemize}
    \item \textbf{\emph{Column Layer}}: per evidenziare le dipendenze tra i singoli attributi;
    \item \textbf{\emph{Observability Layer}}: per integrare direttamente sul grafo gli esiti dei test di \emph{Data Quality}, consentendo di individuare visivamente il punto in cui si è verificata un'anomalia sui dati;
    \item \textbf{\emph{Data Product Layer}}: per evidenziare la composizione e l'origine dei dataset curati messi a disposizione dei vari domini aziendali.
    \item \textbf{\emph{Service Layer}}: per visualizzare come i dati fluiscono attraverso piattaforme e servizi differenti.
    \item \textbf{\emph{Domain Layer}}: per organizzare i dataset e gli asset raggruppandoli all'interno di categorie di business pertinenti.
\end{itemize}
